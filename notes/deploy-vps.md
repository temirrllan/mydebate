# Развёртывание на своём сервере (VPS) — пошагово

Дата: 2026-08-09. Связано: [[deploy-guide]] (объяснение «зачем»), [[deploy]], [[progress]].
Тэги: #deploy #vps #reference

Всё живёт на одной машине: приложение, Postgres и обратный прокси с HTTPS. Neon и Vercel Blob не нужны — база в контейнере, картинки на диске сервера.

Файлы в репозитории:
- `web/Dockerfile` — образ приложения (сборка Next в standalone-режиме)
- `docker-compose.yml` — четыре сервиса: `db`, `migrate`, `web`, `caddy`
- `Caddyfile` — HTTPS и проксирование
- `.env.production.example` — шаблон окружения сервера
- `deploy/backup.sh` — бэкап базы

> ⚠️ Сборка Docker-образа **пока не проверена вживую** — на рабочей машине Docker не установлен. Standalone-сервер Next с Prisma я запускал и проверял отдельно (страницы отдаются, база читается), но саму сборку образа мы увидим только на сервере. Если что-то отвалится — почти наверняка на шаге 5, разберём по логам.

---

## 1. Что понадобится

- **VPS**: 2 ГБ RAM минимум (сборка Next любит память), Ubuntu 24.04. Hetzner ~5 €/мес, из локальных — Timeweb, PS.KZ, hoster.kz (ближе к пользователям = меньше задержка).
- **Домен**, направленный на IP сервера.
- Доступ по SSH.

## 2. Домен

В DNS-панели домена завести **A-запись** на IP сервера:

```
@      A     123.45.67.89
www    A     123.45.67.89
```

Сделать это **до** первого запуска: Caddy при старте попросит у Let's Encrypt сертификат, а тот проверит, что домен указывает на этот сервер. Изменения DNS расходятся от нескольких минут до пары часов. Проверить: `dig +short твой-домен`.

## 3. Подготовка сервера

Подключиться: `ssh root@IP`. Дальше:

```bash
# Обновить систему
apt update && apt upgrade -y

# Docker (официальный скрипт установки)
curl -fsSL https://get.docker.com | sh

# Фаервол: наружу только SSH и веб
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
```

Работать под `root` не стоит — завести пользователя:

```bash
adduser deploy
usermod -aG docker,sudo deploy
# скопировать ключи, чтобы заходить сразу под ним
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy
```

Дальше — под `deploy` (`ssh deploy@IP`).

## 4. Код и окружение

```bash
git clone https://github.com/temirrllan/mydebate.git
cd mydebate
cp .env.production.example .env
nano .env
```

Заполнить (подробности по каждой переменной — в комментариях самого файла):

- `DOMAIN` — домен без `https://`
- `POSTGRES_PASSWORD` — `openssl rand -base64 24`
- `DATABASE_URL` — тот же пароль внутри строки, хост оставить `db`
- `AUTH_SECRET` — `openssl rand -base64 32`
- `AUTH_URL` — `https://твой-домен`
- `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET`, `SMTP_*`, `EMAIL_FROM`

Google OAuth: в Cloud Console добавить в Authorized redirect URIs `https://твой-домен/api/auth/callback/google`, в origins — сам домен.

## 5. Первый запуск

```bash
docker compose up -d --build
```

Первая сборка идёт долго (несколько минут): качаются образы, ставятся зависимости, собирается Next. Порядок такой:

1. поднимается `db` и ждёт, пока Postgres начнёт отвечать (healthcheck);
2. отрабатывает `migrate` — создаёт таблицы через `prisma migrate deploy` и завершается;
3. стартует `web` — только после успеха миграций, поэтому устаревшей схемы он не увидит;
4. `caddy` получает сертификат и открывает сайт наружу.

Смотреть, как идёт:

```bash
docker compose ps          # статусы; migrate должен быть Exited (0)
docker compose logs -f     # все логи
docker compose logs migrate
```

## 6. Первый администратор

⚠️ **`db:seed` на сервере не запускать** — сид удаляет все данные и создаёт демо-пользователей с паролем `password123`.

1. Открыть сайт, зарегистрироваться обычной формой → появится пользователь с ролью `USER`.
2. Выдать себе админа прямо в базе:

```bash
docker compose exec db psql -U mydebate -d mydebate \
  -c "UPDATE \"User\" SET role='ADMIN' WHERE email='твой@email';"
```

3. Перезайти на сайте — роль в сессии обновится.

## 7. Проверка

Главное — **пережить перезапуск**. Пока не проверил, развёртывание рабочим не считается.

- [ ] Сайт открывается по `https://`, замок в браузере есть
- [ ] Регистрация и вход работают (в том числе через Google)
- [ ] Создать турнир с обложкой → картинка видна
- [ ] `docker compose restart web` → турнир и картинка на месте
- [ ] `docker compose down && docker compose up -d` → данные всё ещё на месте (это проверка томов)
- [ ] Письмо сброса пароля доходит
- [ ] Роли: гость / пользователь / организатор / админ — модерация, заявки, уведомления

## 8. Бэкапы — сделать сразу

База на том же диске, что и всё остальное. Умер сервер — умерли данные, и восстанавливать будет нечего.

```bash
chmod +x deploy/backup.sh
./deploy/backup.sh          # проверить, что дамп снимается
crontab -e
# каждый день в 03:30
30 3 * * * cd /home/deploy/mydebate && ./deploy/backup.sh >> backups/backup.log 2>&1
```

Дальше — обязательно настроить выгрузку каталога `backups/` наружу (другой сервер, объектное хранилище, свой ноутбук). Дамп, лежащий на том же диске, не спасает от смерти диска. Заготовки команд — в конце `deploy/backup.sh`.

И хотя бы один раз проверить **восстановление** на пустой базе, пока ничего не горит. Непроверенный бэкап — это не бэкап.

## 9. Обновление приложения

Руками на сервере:

```bash
cd ~/mydebate
./deploy/update.sh
```

Скрипт делает `git merge --ff-only origin/main`, пересобирает контейнеры, показывает логи миграций и чистит старые образы. Голые `git pull && docker compose up -d --build` тоже работают — скрипт просто добавляет проверки.

Миграции применятся автоматически: `migrate` отработает до старта нового `web`. Данные и картинки лежат на томах, пересборка их не трогает.

### Автодеплой по пушу в main

Настроен в `.github/workflows/deploy.yml`: после каждого пуша в `main` GitHub сам подключается к серверу по SSH и запускает тот же `deploy/update.sh`. Заходить на сервер не нужно, ход деплоя виден на вкладке **Actions**.

Разовая настройка — отдельный SSH-ключ **только для деплоя** (не тот, которым вы заходите сами):

```bash
# на своём компьютере
ssh-keygen -t ed25519 -f ~/.ssh/mydebate_deploy -C "github-actions-deploy" -N ""
ssh-copy-id -i ~/.ssh/mydebate_deploy.pub root@IP-СЕРВЕРА
ssh-keyscan IP-СЕРВЕРА            # строки для DEPLOY_KNOWN_HOSTS
```

Дальше в репозитории **Settings → Secrets and variables → Actions** завести секреты:

| Секрет | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP или домен сервера |
| `DEPLOY_USER` | пользователь SSH (`root` или отдельный `deploy`) |
| `DEPLOY_SSH_KEY` | содержимое `~/.ssh/mydebate_deploy` (приватный ключ целиком, вместе со строками BEGIN/END) |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan IP-СЕРВЕРА` |
| `DEPLOY_PATH` | необязательно; каталог с `docker-compose.yml`, если это не `~/mydebate` |

Пуши, которые трогают только заметки и макеты (`**.md`, `notes/`, `maket/`), деплой не запускают — сборка Next на 2 ГБ VPS занимает минуты, тратить их на правку заметки незачем.

Если деплой упал, `web` остаётся на старом образе: сайт продолжает работать на предыдущей версии, ошибка видна в логе job'а.

## 10. Диагностика

```bash
docker compose ps                 # кто жив
docker compose logs -f web        # логи приложения
docker compose logs -f caddy      # проблемы с сертификатом видно здесь
docker compose exec db psql -U mydebate -d mydebate   # консоль базы
docker stats                      # память и CPU
df -h                             # место на диске
```

## 11. Типичные ошибки

| Симптом | Причина |
| --- | --- |
| Caddy не выпускает сертификат | домен ещё не указывает на сервер, или закрыт порт 80 (нужен для проверки) |
| `migrate` падает с ошибкой подключения | пароль в `DATABASE_URL` не совпадает с `POSTGRES_PASSWORD` |
| Сайт отдаёт 502 | контейнер `web` не поднялся — смотреть `docker compose logs web` |
| `UntrustedHost` при входе | не задан `AUTH_URL` |
| `redirect_uri_mismatch` | в Google Console нет redirect URI с прод-доменом |
| Картинки пропали после обновления | том `uploads` не смонтирован (проверить `docker compose config`) |
| Сборка падает по памяти | на VPS меньше 2 ГБ RAM — добавить swap или взять тариф побольше |
| Все вылетели из аккаунтов | сменился `AUTH_SECRET` — нормально, старые сессии инвалидируются |
