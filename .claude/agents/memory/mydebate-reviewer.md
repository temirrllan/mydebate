## Recurring patterns to check first (as of 2026-07-10 full-app review)
- **Date-only deadline fields parsed as UTC midnight**: `<input type="date">` values go through `new Date("YYYY-MM-DD")` (`lib/validations/tournament.ts` dateInputSchema), which yields UTC 00:00. `isRegistrationOpen()` (`lib/format.ts`) then does `deadline.getTime() > Date.now()`, so registration effectively closes at the very start of the deadline day (UTC), not end-of-day — the organizer-selected deadline date itself is barely/not usable for registering. Same pattern likely worth checking anywhere else a date-only field is compared with `Date.now()`.
- **Feature-parity check for organizer-configurable fields**: verify every field captured by a create/edit form is actually *read* somewhere downstream. Found `Tournament.registrationType`/`externalUrl` (PLATFORM vs EXTERNAL registration) captured on create but never branched on in `/tournaments/[id]` or `/tournaments/[id]/register` — CTA always routes to the internal form regardless of organizer's choice.

Worth grepping `prisma.supportTicket.create` across `app/`/`lib/` each review.

## 2026-07-11 deep a11y audit — new recurring patterns to check first
- **No `aria-describedby` anywhere in the codebase** (`grep -r aria-describedby app/ components/` = 0 hits, confirmed again on this pass). `FieldError` (`components/auth/field-error.tsx`) never emits an `id`, so `aria-invalid` on inputs can never be wired to its error text — systemic across every form (login/register/forgot/reset/tournament-register/wizard/contact/moderation reject-reason). Check this first on every future form-touching review; a proper fix is `FieldError` accepting/generating an `id` + callers adding `aria-describedby={errorId}`.
- **Dynamic/live content has zero `aria-live` outside `loading.tsx` skeletons.** Confirmed gaps: catalog "Найдено N турниров" counter (`app/tournaments/page.tsx`) after filter/search, the live password-requirements checklist (register-form.tsx/reset-password-form.tsx), success banners that replace the whole form (create-wizard, contact-form, register-form for tournament) render via plain `<p>`/`<Card>` swap with no `role="status"` and no focus move to the new content, and every "inline row error" (`ModerationTable`, `UserRow`, `CancelRegistrationButton`) is a bare `<p className="text-rose-600">` with no `role="alert"`/`aria-live`. `role="alert"` IS used correctly for the top-of-form error banners in every auth/support form — the gap is specifically in row-level/inline dynamic errors and success replacements.
- **Inline confirm-delete/cancel pattern loses keyboard focus.** Recurring across `CancelRegistrationButton`, `UserRow` (block/delete), `ModerationTable` (delete/reject) — clicking "Удалить"/"Отменить" swaps in a differently-keyed button subtree with no focus management, so keyboard/SR focus drops to `<body>`. Same root cause each time (conditional JSX branch, not a stable focused element) — worth a single shared confirm-button primitive next iteration instead of 3+ hand-rolled copies.
- **Button-group filters (`aria-pressed` pill toggles) lack a `fieldset`/`legend` or `role="group"`+`aria-labelledby`.** Pattern in `step1-basic-info.tsx` (Формат/Тип проведения/Языки турнира) and `step3-contacts.tsx` (Способ регистрации) — the group caption is a plain `<span>` with no programmatic tie to the button group.
- **Opacity-reduced `text-muted` fails contrast on light backgrounds but passes on navy.** `placeholder:text-muted/70` (used in literally every `Input`/`Select`/textarea, `components/ui/input.tsx:13`) computes to ~2.7:1 against white. `text-muted/80`/`/60` used on `bg-navy-900` hero/profile-header blocks are all comfortably >6:1 — don't flag navy-block opacity text again, only flag `text-muted` opacity variants over light/white surfaces.
- **`prefers-reduced-motion` is only actually honored for `.animate-fade-in`** (`app/globals.css`) — every `loading.tsx` skeleton (`animate-pulse`) and every spinner (`animate-spin`, e.g. `Loader2` in admin action buttons) ignores the user's OS preference. Spec/claims say reduced-motion is respected; it's only partially true — check this every time before accepting that claim.

Support-ticket submission (`/contacts` → `ContactForm` → `createSupportTicket`) is also now wired — resolved, don't re-flag.
