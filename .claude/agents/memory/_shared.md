# Shared memory — MyDebate multi-agent system

Cross-agent conventions and decisions that every agent must respect. Keep entries short and high-signal. Add a line here only when a decision affects more than one agent.

## Stack (fixed)
- Next.js 15 (App Router) + React + TypeScript
- API: Route Handlers + Server Actions (no separate backend server)
- DB: PostgreSQL + Prisma
- Auth: NextAuth (email+password + Google OAuth)
- Styling: Tailwind CSS
- File uploads: UploadThing or S3 (covers/logos/avatars)

## Enums (source of truth — mirror in Prisma)
- Role: `USER | ORGANIZER | ADMIN` (Guest = unauthenticated)
- Tournament format: `DEBATES | MUN`
- Tournament type: `ONLINE | OFFLINE`
- Tournament status: `DRAFT | PENDING | PUBLISHED | REJECTED | HIDDEN | DELETED`
  - `REJECTED` = отклонён модерацией (причина в `rejectionReason`), `HIDDEN` = снят с публикации админом уже после одобрения. Раньше отказ писался как `HIDDEN` + `rejectionReason` — эта конвенция отменена (2026-07-13); `getTournamentStatusDisplay` всё ещё распознаёт старую пару ради исторических записей.

## Cross-agent contracts (fill in as built)
- Auth helpers (Этап 2, `web/lib/auth/session.ts` — all `import "server-only"`, Server Components/Actions/Route Handlers only):
  - `getCurrentUser(): Promise<CurrentUser | null>` — `CurrentUser = { id, email, firstName, lastName, role, isBlocked, image }`. Null for guest AND for a since-blocked user (re-checks DB, doesn't just trust the JWT).
  - `requireUser(callbackUrl?: string): Promise<CurrentUser>` — redirects guest to `/login?callbackUrl=...`.
  - `requireRole(role: string | string[], callbackUrl?: string): Promise<CurrentUser>` — redirects guest to `/login`, wrong-role authenticated user to `/403`.
  - `requireAdmin(callbackUrl?: string): Promise<CurrentUser>` — shorthand for `requireRole(Role.ADMIN, ...)`.
  - Role escalation: `web/lib/auth/roles.ts` → `maybePromoteToOrganizer(userId: string): Promise<void>` (USER→ORGANIZER after first PUBLISHED tournament) — **wired up as of Этап 6**: called from `approveTournament` in `web/lib/actions/admin.ts` right after setting `Tournament.status = PUBLISHED`.
  - NextAuth v5 (`web/auth.ts`): `auth()`, `signIn()`, `signOut()`, `handlers` exported. Session strategy JWT; `session.user` has `id` and `role` (string, one of `Role`). Credentials-only for now (no Google yet).
  - Route protection lives in `web/proxy.ts` (Next 16 renamed file, not `middleware.ts`) — see `mydebate-auth.md` for the exact public/protected/admin path lists. **If you add a new top-level protected section, you must add its prefix to `proxy.ts` yourself** — the default for unlisted paths is permissive (public), not restrictive.
- Shared types location: `web/types/next-auth.d.ts` (Session/JWT/User augmentation only so far). No general shared-types folder yet.
- Backend routes/actions the frontend calls (Этап 4, full detail in `mydebate-backend.md`):
  - `web/lib/tournaments/queries.ts`: `listTournaments(params?)`, `getAvailableCities()`, `getTournamentDetail(id)` — catalog + detail data, PUBLISHED-only, call directly from Server Components.
  - `web/lib/actions/registrations.ts`: `registerForTournament(tournamentId, prevState, formData)` (bind tournamentId, `useActionState`-shaped) and `cancelRegistration(tournamentId)`. Success message is spec-exact, exported as `REGISTRATION_SUCCESS_MESSAGE`.
  - `web/lib/actions/favorites.ts`: `toggleFavorite(tournamentId)`, `getFavoriteTournamentIds(userId)` (for marking hearts active in the catalog without N+1).
  - `web/lib/actions/notifications.ts`: `markNotificationRead(id)`, `markAllNotificationsRead()`.
  - `web/lib/notifications/create.ts`: `createNotification({userId,type?,title,message,link?})` — reuse this for any future in-app notification instead of calling prisma directly.

  - **Schema change**: `Registration` model gained nullable snapshot fields (`fullName, gradeOrCourse, schoolOrUniversity, phone, contactEmail, teamName, teammateNames, experienceLevel, preferredLanguage, additionalInfo`) to store the registration-form submission (migration `20260707153408_registration_form_fields`). The mockup's payment/receipt-upload step is deliberately NOT implemented (payment deferred per task instruction).
- **`"use server"` files must only export async functions — enforced at BUILD time, not just lint, in this Next/Turbopack version, and ONLY once the module is pulled into a client bundle** (e.g. a client component imports one of the file's actions for `useActionState`). A co-located `export const SOME_STRING = "..."` in the same file then breaks the **entire build** (every export of the file, including the async ones, reports as "doesn't exist"). Discovered when wiring `registerForTournament` into a client form: `lib/actions/registrations.ts` had `export const REGISTRATION_SUCCESS_MESSAGE`, moved (text unchanged) to `lib/format.ts` (plain module) instead — `lib/actions/registrations.ts` now imports it from there rather than defining/exporting it. **Audit any `lib/actions/*.ts` file for this pattern before binding one of its functions into a client component** — non-function `export const`s must live in a plain module, not the `"use server"` file, if that file's functions are ever used client-side.

## Data layer (Этап 1 — done, see mydebate-database.md for full detail)
- DB is currently **SQLite** for dev (`web/.env` DATABASE_URL="file:./dev.db"), not Postgres yet — schema/enums are Postgres-migration-ready but all "enums" are plain `String` fields (SQLite has no native enum). Mirror TS constants in `web/lib/enums.ts` — always import enum values from there, never hardcode string literals.
- Prisma client singleton: `import { prisma } from "@/lib/prisma"`. Do NOT import `PrismaClient` directly from `@/generated/prisma` (bare path 404s) — always `@/generated/prisma/client` if you ever need the class itself, and only the singleton needs the driver-adapter wiring (`@prisma/adapter-better-sqlite3`).

## Key spec rules everyone must honor
- Guests cannot view the tournaments catalog (auth-gated).
- Public queries return only `PUBLISHED` tournaments.
- Post-publish, only description + info sections are organizer-editable; date/price/venue change only via support.
- After a user's first approved tournament, their role auto-becomes ORGANIZER.
- Registration closes when `now > registrationDeadline`.
- Exact user-facing messages are in the spec — copy them verbatim.
